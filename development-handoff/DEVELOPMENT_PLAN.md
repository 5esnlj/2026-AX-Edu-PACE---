# 가나다계단 다음 개발 계획

기준일: 2026-11-21. 이번에 전달받은 React + TypeScript + Vite 소스, 기존 MariaDB 20개 테이블 DDL·DML, 사용자 확정 요구를 기준으로 작성했습니다. 첨부 설명서의 오래된 요구보다 이후 확정한 요구를 우선합니다.

## 1. 지금 어디까지 되어 있나

| 영역 | 현재 상태 | 실제 서비스까지 남은 것 |
|---|---|---|
| 디자인·공통 부품 | 로고, 디자인 토큰, 카드·버튼·표·사이드바 등 있음 | 접근성·화면 크기 대응·공통 상태 검증 |
| 화면 | 원본에는 교사 대시보드, 교사 자료 목록, 학생 대시보드 3개 | HANDOFF의 나머지 16개 화면과 누락된 상세·실패 화면 |
| 이번 FE 수정본 | 위 세 화면을 HTTP mock에 연결; 로그인·클래스 선택을 위한 연동 확인 UI 추가 | 정식 가입·초대·진단·생성·풀이 화면을 완성한 것은 아님 |
| API | 41개 동작의 명세와 실행 가능한 메모리 mock | 실제 DB를 사용하는 서비스·저장 계층 구현 |
| DB | MariaDB 11.8 기준 20개 테이블 DDL, 기능별 DML 기준 문서 | 마이그레이션 관리, 실제 데이터 연결, 트랜잭션·동시성 통합검증 |
| 진단 | 일회성 진행 저장·채점의 mock 계약 있음 | 공식 문항·정답·배점·판정 문항·음원 탑재 및 교육 담당자 검수 |
| AI·파일 | 가상 생성·업로드 계약 있음 | 실제 PDF 추출/비공개 저장, Solar 호출, 비동기 작업 복구 |
| 운영 | 로컬 검증용 | HTTPS 배포, 계정 발급, 백업·복원, 관측·운영 절차 |

**API mock이 통과했다는 것은 실제 백엔드가 완성됐다는 뜻이 아닙니다.** 서버를 재시작하면 mock의 생성·답안·로그인 정보는 초기화됩니다. 원본 UI의 버튼 대부분은 빈 함수였으며, 이번 연결본에서 아직 제공하지 않는 기능은 비활성화하고 사유를 표시합니다.

## 2. 유지할 서비스 범위

- 교사가 클래스 개설 → 역할별 초대 → 학생이 클래스 참여 → 최초 진단 → 교사가 학생별 자료·문제 생성 → 검토·배포 → 학생이 확인·풀이.
- 교사 자료·문제·학습 활동은 해당 클래스의 담당 교과만 조회. 클래스 소유자도 다른 교과에 대한 예외 없음.
- 학생별 진단은 계정당 한 번. 5영역 × 듣기·읽기 = 파트 결과 10개, 같은 영역의 종합 결과 5개. 4수준과 진단 미완료를 구분.
- 생활한국어도 확정된 5영역 중 하나. 전체 교과를 평균 내어 별도의 단일 수준을 만들지 않음.
- 학생별 자료와 T/F 또는 4지선다 문제를 저장. 학생은 AI 생성을 요청하지 않음.
- 첫 성적은 재풀이로 덮어쓰지 않음. 현재 남은 오답과 재풀이 횟수는 각각 조회.
- 배움길·메시지·오역탐지·단어 기록·말하기/쓰기·반복 진단은 제외.

## 3. 권장 구현 순서와 완료 기준

### 1단계 — 계약과 실행 환경을 고정

**작업:** 이번 OpenAPI와 FE 변환 코드를 기준으로 사용합니다. Python FastAPI mock과 운영 서버 코드는 구분하고, 기존 Python 기능을 이어 쓴다면 FastAPI + MariaDB로 시작하는 것이 재사용에 유리합니다. HeidiSQL은 DB 관리 도구이며, 실제 서버는 앞서 확인된 MariaDB 11.8입니다. 화면명과 테이블명을 이유로 DB 제품을 바꿀 필요는 없습니다.

**산출물:** frontend/backend 디렉터리 또는 별도 저장소, 환경별 설정, 마이그레이션, CI의 타입 검사·API 계약 테스트.

**완료 기준:** 새 개발 PC에서 문서만으로 FE·mock·개발 DB를 띄울 수 있고, 계약 테스트가 자동 실행됩니다. 실제 계정·학생 데이터·API 키는 예제나 저장소에 넣지 않습니다.

### 2단계 — 로그인·클래스·초대를 실제 DB로 연결

**백엔드:** users/user_sessions와 클래스 3개 테이블을 기존 DML에 연결합니다. 비밀번호 해시, 세션 생성·만료·취소, 교사 확인 상태, 초대 만료·사용 횟수·역할을 처리합니다. 클래스 개설과 소유자 소속 생성은 한 트랜잭션입니다.

**프론트:** 정식 로그인, 클래스 목록/선택, 클래스 개설, 교사 공유·학생 초대 수락. 서버의 nextAction에 따라 가입·진단·학습을 구분합니다.

**추가 결정:** 실제 회원을 누가 발급할지 아직 실행형 API에 없습니다. 초기 학교 실증은 운영자가 승인 계정을 발급하고 교사가 클래스 초대를 보내는 방식으로 시작할 수 있습니다. 공개 회원가입을 제공하려면 가입·교사 승인·비밀번호 재설정의 화면/API·검증 수단을 별도 설계해야 합니다. 로그인 선택 탭만으로 교사 권한을 주면 안 됩니다.

**DB 보완:** 교사 초대에 담당 교과를 고정하는 제안은 `api/BACKEND_ADAPTER_NOTES.md`를 따릅니다. 기존 DDL을 몰래 변경하지 않았으므로 마이그레이션으로 별도 반영합니다.

**완료 기준:** 서버 재시작 후에도 계정·소속이 남고, 만료/역할이 다른 초대가 거부됩니다. 다른 클래스·다른 교과 URL을 직접 요청해도 서버에서 차단됩니다.

### 3단계 — 최초 진단과 이어하기를 완성

**백엔드:** 공식 문항집 버전을 고정하고 답안을 문항별로 저장합니다. 제출하지 않은 첫 문항을 반환합니다. 마지막 답안 저장·파트10개·종합5개·완료 상태를 한 트랜잭션에서 확정합니다. 정답·배점·판정 규칙은 서버에서만 사용합니다.

**프론트:** 진단 화면, 듣기 재생, 진행률, 저장 실패 시 재시도, 진단 결과와 교사 학생 수준표. 진단 미완료 학생은 다시 로그인해도 다음 미제출 문제부터 시작합니다.

**완료 기준:** 중간 종료·새로고침·중복 전송·두 탭 동시 제출에서 답안 누락이나 중복 채점이 없습니다. 5개 영역 모두 실제 루브릭의 점수 경계·과락 사례를 검증합니다. 문제 수는 서버 값이며 mock의 70문항을 공식 문항 수로 확정하지 않습니다.

### 4단계 — 자료 업로드부터 학생별 배포까지 연결

**백엔드:** PDF 형식·크기 확인, 비공개 파일 저장, 본문 추출, 원본 등록. 교사 본인의 Solar 키를 서버에서 암호화 보관하고, 요청 시점의 모델·키·학생 언어·진단 스냅샷을 고정합니다. 생성은 웹 요청과 분리된 작업으로 실행하고 queued/running/succeeded/failed 상태를 DB에 저장합니다. 긴 외부 API 호출 중에는 DB 트랜잭션을 열어 두지 않습니다.

**프론트:** 업로드, 진단 완료 학생 선택, 생성 진행·일부 실패, 학생별 원본/전환본 비교, 수정·검토·배포, 학생 받은 자료 목록/상세. 하나의 원본을 클릭하면 그 원본에 속한 학생별 결과를 고르는 흐름으로 연결합니다. sourceId를 materialId처럼 사용하지 않습니다.

**완료 기준:** 여러 학생에게 각각 다른 결과가 저장되고, 교사 검토 전에는 학생에게 보이지 않습니다. 검토 후 수정은 검토 상태를 해제합니다. 오래된 편집 화면은 If-Match 충돌로 알려 줍니다. 작업 중 서버가 재시작되거나 외부 응답을 받지 못한 경우 중복 과금 가능성을 고려해 복구하며, 무조건 자동 재호출하지 않습니다.

### 5단계 — 자료 기반 문제 생성·풀이·재풀이 완성

**백엔드:** 원본 PDF 또는 학생별 전환본에서 T/F·4지선다 생성 → 보기 수·정답 ID·출처·해설 구조 검증 → 초안 저장 → 교사 검토 → 배포. 문항별 답안을 저장하고 첫 성적·최신 오답·재풀이 횟수를 분리합니다.

**프론트:** 문항 목록/생성/검토/수정, 학생 문제 풀이·결과·해설·오답 다시 풀기. T/F는 보기2개, 4지선다는 보기4개입니다. API의 첫 성적과 현재 오답을 같은 값으로 취급하지 않습니다.

**완료 기준:** 학생이 다른 학생의 문항이나 제출 전 정답을 가져올 수 없습니다. 같은 요청 재전송으로 재풀이 수가 증가하지 않습니다. 재풀이로 정답을 맞혀도 처음 점수는 보존됩니다. 배포한 문항은 덮어쓰지 않습니다.

### 6단계 — 학교 사용 전 통합 검증·배포

**작업:** 교사·학생 두 계정으로 위 전체 흐름을 검증합니다. 학교 PC 브라우저, 키보드 조작, 작은 화면, 긴 한글·번역문, 느린 네트워크를 확인합니다. HTTPS로 FE/API를 같은 도메인에 제공하고 DB·파일 저장소는 외부에 직접 공개하지 않습니다.

**운영 완료 기준:** 백업 복원 실습, 세션 만료/로그아웃, 계정 비활성화·클래스 종료, 보존/삭제 절차, 학생 개인정보 접근 범위, 비용 한도·Solar 실패 알림, 로그의 키·답안 원문 노출 방지까지 실제 배포 환경에서 확인합니다. 초기에는 한 클래스의 제한된 사용자로 운영하고 발견된 문제를 고친 후 확대합니다.

## 4. 병렬로 진행할 일

프론트 담당자는 mock을 유지한 채 아직 없는 화면을 구현하고, 백엔드 담당자는 같은 OpenAPI 응답을 MariaDB로 교체할 수 있습니다. 교육 담당자는 공식 진단 문항·음원·정답표·루브릭 경계 사례와 자료 변환 품질 평가 예제를 준비합니다. 운영 담당자는 계정 발급 방식·학교 배포 도메인·키/비용 정책·데이터 보존 기준을 정리합니다.

우선 완성할 첫 단위는 **교사 로그인 → 클래스 개설 → 학생 초대 수락 → 최초 진단 저장·재개**입니다. 이 흐름이 실제 DB에서 확인된 다음 AI 자료 제작을 연결하면, 학생·소속·진단이 없는 상태에서 생성 기능을 먼저 붙여 생기는 재작업을 줄일 수 있습니다.

## 5. 이번 변경으로 DB를 새로 만들 필요가 있나

없습니다. 이번 API의 className은 classes.name, diagnosticStatus는 student_diagnostics.status, unit은 source_materials.unit에서 조회합니다. 요약 타일·진행률·수준별 인원·화면 라벨은 조회 또는 FE 변환 결과이며 새 테이블이 아닙니다.

20개 테이블과 DML 기준은 `api/baseline/`에 그대로 보존했습니다. 이전부터 남아 있던 교사 초대 교과 저장, 생성 요청의 입력 JSON 구조, 수정 버전 비교는 `api/BACKEND_ADAPTER_NOTES.md`의 후속 작업입니다. 회원가입·운영 관리처럼 아직 없는 기능을 이번 41개 API에 이미 구현된 것으로 계산하지 않습니다.
