# API 설계 기준과 화면 자료의 차이

이 문서는 이번 작업에서 API 명세가 어떤 기준을 따르는지 기록합니다. 이후 백엔드 개발 시 대화 기억에 의존하지 않고 이 파일, OpenAPI 명세, DML을 함께 사용합니다.

## 기준 우선순위

1. 사용자가 대화에서 확정한 기능 범위와 최근 변경.
2. 검토를 거쳐 만든 MariaDB 20개 테이블 및 `가나다계단_DML_설계.md`의 데이터 관계·권한·트랜잭션 규칙.
3. 첨부 `HANDOFF.md`의 19개 화면·버튼·필요한 정보.
4. 첨부 화면의 예시 인물·숫자·수치·미정 표기.

첨부 `시작하기.md`와 `CLAUDE.md`는 전달 자료의 사용 안내와 프론트 코딩 규칙입니다. 이번 요청은 API 설계·mock 데이터·테스트이므로 해당 문서의 프로젝트 파일 덮어쓰기, 외부 도구 설정, 화면 코드 변경을 별도 사용자 지시로 해석하지 않습니다.

## 반드시 유지하는 확정 조건

| 삭제 범위 | 배움길·메시지·오역탐지·아는/모르는 단어 기록·학생 AI 생성은 제외 |

## 화면 자료와 충돌하는 부분의 처리

### 1. 교사 자료 접근

HANDOFF는 다른 교과를 아래에 나열하지만 사용자 최신 요청은 **자기 교과만 조회**입니다. 자료 목록뿐 아니라 전환본·문제·최근 풀이·파일 다운로드·AI 요청 원본에도 같은 조건을 적용합니다. 클래스 소유자도 다른 교과 열람 예외가 없습니다. 다른 교사가 만든 같은 교과 자료는 접근할 수 있습니다.

### 2. 생활한국어

HANDOFF의 ‘기준 미정 → – 표시’는 이전 상태입니다. 사용자 확정은 생활한국어도 다른 네 교과와 동일하게 듣기/읽기 점수 및 최종 수준을 갖는 구조입니다. 진단을 마친 학생에게 daily 데이터를 누락하지 않습니다. 진단 미완료를 ‘초급 미달’이나 점수0으로 표현하지 않습니다.

### 3. 전체 등급처럼 보이는 카드

사용자가 확정한 종합은 **영역별 종합5개**입니다. 국수사과생활을 다시 합친 하나의 종합 점수/수준은 없습니다. 세 카드(듣기·읽기·종합)는 선택한 영역의 세 결과를 보여 줍니다. 교사 대시보드의 기본 영역은 담당 교과로 제안하고, 학생 화면에는 영역 선택을 표시합니다. 학생 대시보드의 기본 영역은 생활한국어(daily)로 제안합니다. 진단 결과 API는 5영역 결과를 반환하고 화면이 선택 영역을 표시하며 임의 평균으로 등급을 만들지 않습니다.

### 4. 초급 미달과 과락

점수 경계만으로 판정하지 않고 확정된 난도별 판정 문항 통과 조건을 적용합니다. 초급 기준 실패는 below_beginner, 고득점이어도 중/고급 조건 실패 시 수준이 내려갑니다. 종합은 같은 영역의 한 파트30점 미만이면 초급, 그 외 합계80/140 경계입니다. **파트 초급 미달을 종합에 자동 전파하지 않습니다.** 현재 종합 규칙에서 below_beginner가 산출되지 않더라도 파트에는 존재하므로 UI 라벨을 세 가지로 제한하지 않습니다.

교사 요약 카드·필터는 어떤 영역/파트/종합을 기준으로 인원을 세는지 명시합니다. 미완료는 별도 인원으로 계산합니다. 종합 기준으로 묶었을 때 초급 미달 인원이0인 것은 데이터 오류가 아닙니다.

### 5. 진단 문항 수와 진행률

시안의 ‘3/20’은 예시입니다. API가 현재 고정 문항집의 total_questions와 completed_questions를 반환합니다. 전체 완료와 총배점·판정 문항 구성을 서버에서 검증합니다. 공식 문항이 준비되지 않은 mock은 가상 문항임을 명시하며 실제 평가 도구로 배포하지 않습니다.

### 6. 점수와 정답 개수

DB는 가중 배점도 지원합니다. ‘8/10 맞았어요’는 정답 문항8개/총10개이며 점수8/총점10과 항상 같지는 않습니다. API는 최초 정답 개수, 총문항 수, 최초 점수, 총점을 구분합니다. 결과 화면은 처음 푼 결과를 보존하고 현재 정답/오답 상태는 별도 필드로 표시합니다.

### 7. 완료 상태와 재풀이

quiz_submissions.completed는 모든 문항의 **첫 답안이 저장됨**을 뜻합니다. 모두 정답이라는 뜻은 아닙니다. 화면의 풀기 전/진행 중/재풀이 있음/모두 정답은 최초 응답 수와 최신 정오에서 계산합니다.

재풀이 버튼 클릭은 DB 쓰기가 아닙니다. 유효한 답안 저장 수−1로 재풀이 수를 계산합니다. 동일 요청키 재전송·실패한 요청·해설 열람은 횟수를 올리지 않습니다. 직전 답이 정답이면 오답 재풀이 API를 거절합니다.

### 8. NEW와 ‘오늘 할 일’

현재 DB에는 자료 읽음 이력이나 학습 마감일/일정이 없습니다. 따라서 NEW는 ‘미열람’으로 주장하지 않습니다. **최근 배포** 표시는 서버 현재 시각 기준 최근7일 배포된 자료의 `isRecentPublished`로 제안합니다. 읽음 이력을 원하면 별도 데이터 모델이 필요합니다.

‘오늘 풀 문제’는 실제 일정 배정이 없어 ‘아직 풀지 않은 문제’로 표기하는 것을 제안합니다. 미응답 문항 수, 최신 오답 문항 수, 미완료 묶음 수를 분리하여 제공합니다.

### 9. 썸네일·단원 번호

원본에는 title, unit, source_text, source_file_id가 있지만 별도 unit_number/thumbnail_url 컬럼은 없습니다. unit은 자유 텍스트로 제공하며 숫자를 지어내지 않습니다. 썸네일은 PDF의 비공개 미리보기 파생 자산을 구현한 경우에만 제공하고, 이번 기본 mock은 명시적 예시 또는 null과 대체 카드를 사용합니다. UI를 위해 DB에 존재하지 않는 값이 실제 저장되는 것처럼 표현하지 않습니다.

### 10. 자료 보기 도구

단어장·단어 안다/모른다 기록은 삭제 범위이므로 API를 추가하지 않습니다. 글자 크기는 브라우저 표현입니다. 듣기는 브라우저 TTS 또는 별도 음성 생성 기능을 선택해야 하며 이 문서에서 구현 완료된 서버 기능으로 간주하지 않습니다. 필기 저장은 현재 테이블에 없습니다. 번역본은 전환 결과에 실제 포함된 번역만 표시하고, 없는 학생용 AI 생성 기능을 새로 만들지 않습니다.

### 11. 공동 교사 초대와 담당 교과 승인

class_invitations에는 invited_role만 있고 초대에 지정한 교과 컬럼이 없습니다. 교사에게 자기 교과 접근만 허용하려면 **초대 수락자가 임의로 교과를 정해 권한을 얻으면 안 됩니다.** 현재 DML은 소유자가 확인·승인한 담당 교과를 사용한다는 전제입니다.

학생 초대는 기존 DML을 그대로 사용할 수 있습니다. 이번 API 초안은 교사 초대 발급 시 클래스 소유자만 `teacherSubject`를 지정하고, 수락자는 교과를 바꾸지 못하도록 제안합니다. mock은 이를 메모리에 저장하여 흐름을 검증합니다.

이를 실제 DB에 반영하려면 **`class_invitations.teacher_subject_code`(nullable, 5교과 enum)를 추가하고 teacher 초대에서는 필수·student 초대에서는 NULL인 제약을 두는 최소 DDL 보완**이 필요합니다. 새 테이블은 필요하지 않습니다. 이 변경은 이번 작업에서 실제 DDL/사용자 DB에 적용하지 않았습니다. ‘기존 20개 테이블만으로 이미 교사 초대의 교과까지 영속 저장됨’이라고 표현하지 않습니다. DB 보완 없이 운영한다면 기존 DML의 소유자 승인 절차가 별도로 필요하며, 수락자의 임의 교과 값을 신뢰하면 안 됩니다.

### 12. 여러 학생 생성과 배포

한 PDF에서 여러 학생을 선택해도 DB의 ai_requests/student_materials/quizzes는 학생별 데이터입니다. 응답은 학생별 작업 ID와 성공/실패를 구분해야 합니다. 생성 작업 그룹을 화면에서 묶는 것과 새 DB 배치 테이블을 도입하는 것은 별개입니다. 일부 학생 생성 실패 시 성공한 다른 학생의 상태를 지우거나 전체 성공으로 표시하지 않습니다.

배포도 특정 학생별 전환본/문제 버전을 대상으로 합니다. 검토된 버전과 배포할 버전이 같은지 확인하며, 검토 뒤 수정하면 검토를 해제합니다. 배포한 내용·정답은 고정하고 변경본은 새 버전/새 묶음입니다.

## 문서에 없는 기능을 추가하지 않는 범위

- 상단 알림 벨만으로 새로운 메시지/알림 이력 테이블을 추가하지 않습니다.
- 상단 검색은 허용된 클래스 자료/문제 범위 검색으로 제한하는 것을 제안합니다. 전역 다른 클래스 검색을 열지 않습니다.
- 학생 개인 상세, 만든 자료 읽기 전용 상세, 생성 대기·오류·빈 화면은 HANDOFF에서 미설계입니다. API를 제공할 수 있어도 화면이 이미 설계되었다고 표현하지 않습니다.
- 색·폰트·로고·아이콘·반응형 레이아웃은 프론트 디자인 요소입니다. API나 DB 필드로 복제할 필요가 없습니다.

## 검증해야 할 API 흐름

1. 로그인 화면의 역할을 바꿔 보내도 실제 계정 역할은 바뀌지 않는다.
2. 진단이 없는 학생은 클래스 가입 → 진단 시작, 진행 중 학생은 다음 미제출 문항, 완료 학생은 학습으로 이동한다.
3. 교사는 자기 교과 자료·문제·파일만 조회하며 URL ID 직접 입력도 차단된다.
4. 생활한국어를 포함해 완료 진단의 파트10개·종합5개가 존재한다.
5. 교사 검토 전 초안은 학생에게 보이지 않고 다른 학생 배정 자료도 보이지 않는다.
6. 원본 직접 출제와 전환본 출제가 각각 올바른 지문·대상 학생을 유지한다.
7. 문제 제출 전에는 정답/해설이 학생 응답에 없고 첫 제출 이후 해당 문항 해설만 볼 수 있다.
8. 오답→오답→정답 제출 시 재풀이2회, 최초 점수 유지, 최신 정답으로 표시한다.
9. 동일 요청키를 재전송해도 제출 수·AI 작업 수가 늘지 않는다. 같은 키의 다른 내용은 충돌 처리한다.
10. 생성 일부 실패, 배포 충돌, 만료 초대, 비활성 소속을 구분하여 응답한다.

## 피그마 확인 한계

직접 확인한 것은 업로드된 화면 설명서의 텍스트·프레임 ID입니다. Figma 연결 요청은 승인되었지만 도구가 활성화되지 않았고, 직접 URL 읽기도 네트워크 프록시에서 403으로 차단되었습니다. 따라서 실제 캔버스와 시각 프레임은 미열람이며 직접 읽었다고 주장하지 않습니다. 연결이 완료되면 실제 화면의 필드·탭·상태와 이 설계의 차이를 다시 대조할 수 있습니다. 이 제한은 API의 데이터 관계를 확정하는 근거와 구분합니다.
